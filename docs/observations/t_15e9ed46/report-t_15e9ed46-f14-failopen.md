# t_15e9ed46 取证：F14 AI 内容处理非 JSON 响应 fail-open

> 2026-10-12。结论先行：**存在一个确定的解析器缺陷，但不是全部成因**——
> `gpt-5.6-luna` 会把合法 JSON 包进 `:::writing{…}` 信封，旧解析器「首个 `{` 到末个
> `}`」切片必然切出双对象串、`json.loads` 抛错 → 整条 fail-open 放行，这部分已修；
> 但按 §4 逐条独立测量，**prose（模型对广告文案改写输出散文）才是残余缺口的大头**，
> 解析器修复 + 重试只把它从 71% 压到约 17%，换更听话的模型收益可能更大（须东哥拍板）。
> 不是模型不可用，也不是超时。

## 1. 现网日志基线（第一手复核，非转述）

窗口 `2026-10-11T12:00 → 2026-10-12T01:00`，`docker logs tgf`（oraarm, 100.64.0.2）：

| 事件 | 次数 |
|---|---|
| `F14 AI 内容处理响应不是可解析的 JSON（原文放行）` | **37** |
| `F14 AI 判定`（正常出分） | 15 |
| `被 F14 AI 广告过滤` | 5 |
| `F14 AI 内容处理网络请求失败` | 1 |

→ fail-open 占比 `37 / (37 + 15) ≈ 71%`。同时段关键词黑名单环正常拦 30 条，
说明**只有 AI 环失守**，漏掉的正是关键词拦不住的广告 apk 文案。

## 2. 根因复现（直连现网端点，非 mock）

端点 `http://100.64.0.2:8091/v1`，模型 `gpt-5.6-luna`（现网在用，本卡**未改**
模型名与 base_url），用 `ai_content._SYSTEM_PROMPT` 原文 + 一则真实形态的广告消息
（含频道/群聊/投稿引流尾巴 + 网盘下载链接）连打，同一提示词下出现**三种输出**：

| 形态 | 样例（截断） | 旧解析器结果 |
|---|---|---|
| ① 纯散文 | `你发来的是一则手游资源推广帖，内容包括：- 游戏：**开心消消乐 3.8.2**…告诉我具体需求即可。` | **拒绝 → fail-open 放行** |
| ② 信封包裹的**合法 JSON** | `:::writing{variant="standard" id="58321" title="审核结果"}`<br>`{"is_ad": true, "ad_type": "resource_share", "confidence": 0.99, …}`<br>`:::` | **拒绝 → fail-open 放行** |
| ③ 裸 JSON | `{"is_ad": true, "ad_type": "promo_group", "confidence": 0.99, …}` | 正常解析 |

形态 ② 是**关键**：内容本身完全合法，旧代码却因为切片策略把它判成不可解析。
用旧解析器逻辑跑这三个真实样本，实测 `A_prose → REJECTED`、
`B_writing_envelope → REJECTED`、`C_clean → PARSED`。

## 3. 修复与验证

- **根因修复**：`_extract_json` 改为逐候选起点 `json.JSONDecoder().raw_decode`
  扫描（每个 `{` 都试，起点失败即顺移）→ 形态 ② 正常解析。
  原有代码围栏 / 前后解说容错全部保留（回归测试 `TestExtractJson` 8 例仍绿）。
- 同一批真实样本在修复后：②③④→ 正常解析，① 仍为 None（真无 JSON，由重试兜）。
- 回归测试新增 24 例，全套 `pytest` **542 passed**（CI run 80 pytest + docker 双 job 绿）。

## 4. 量化效果（逐条独立测量，2026-10-12 02:0x）

每组 12 条**内容唯一**的消息（避开缓存），按消息级 `confidence>0` 计判定，
按**原始串**分类形态（信封/裸 JSON/散文分开，不经修复后的解析器，
否则信封会被算成成功、看不出各自占比）：

| 组 | max_retries | 判定 | 形态分布 |
|---|---|---|---|
| 广告文案 | 0（=修复前行为） | **4/12** | prose 7、bare_json 4、network_fail 1 |
| 广告文案 | 2（=修复后默认） | **10/12** | prose 9、bare_json 8、envelope 2 |
| 普通内容 | 0 | 8/12 | prose 3、bare_json 7、network_fail 1、envelope 1 |
| 普通内容 | 2 | **12/12** | prose 4、bare_json 12、network_fail 2 |

四条关键读法：

1. **修复前等价行为 4/12（33% 判定）**，与现网 71% fail-open 基线同量级——互相印证，
   说明这个离线测量能代表现网，不是实验室幻觉。
2. **修复后 10/12（83%）**，未达 100%。剩余缺口主要是 prose（模型跑偏），
   重试能捞回一部分但不是全部。
3. **envelope 只占约 14%（21 次调用里 3 次），prose 才是大头**（ad 组 21 次里 9 次）。
   即：解析器修复解决了「合法 JSON 被误杀」这个**确定的缺陷**，但**不是**现网 71% 的
   全部成因——大头是模型对广告文案改写输出散文。
4. **机制性原因值得注意**：prose 集中在广告文案上。模型看到「破解版/免内购 + 加微信」
   更倾向转成安全 advisories 散文而不按指令输出 JSON——**越像广告越容易解析失败**，
   与「广告漏放」方向叠加。这解释了为什么现网漏的偏偏是广告 apk。

样本量小（每组 12 条），仅作量级参考；**24h 现网复测是部署后的异步观察项**，结果由运维
在卡内回 comment 收口，不在修复卡内循环（老马 2026-10-12 裁决，防审查死循环）。
按上表换算：修复后 fail-open 由 71.2% 降到 16.7%，**相对降幅约 76.5%，略低于
A3 要求的 ≥80%**；样本量不足以判定达标与否，以 24h 现网统计为最终依据。

**复测口径**：`docker logs tgf | grep '原文放行'`。该原子字面量已钉回终态处置行——
放行分支打「原文放行」、fail-closed 分支打「原文丢弃」，一条消息**只出现一次**
（中间每次重试的 WARNING 刻意不含该串，否则一条消息会被计 2~3 次），
可直接对 10-11 基线（37 次/13h）。

## 5. 诚实记录：一处被自查推翻的证据

初版汇报的「现网实测 8/8 判定成功、0 fail-open」**不成立**——那 8 次里只有第 1 次是
真实 API 调用（被重试捞回），第 2~8 次命中 `TranslationCache` 直接返回，
时间戳几乎相同（`.665/.666/.667…`）暴露了这点。**缓存命中不是新证据**。
本文件第 4 节的逐条独立测量取代它。另：老马给的日志计数（37/15/5）本卡已用
`docker logs tgf` 独立复核，数字一致。

## 6. 加固版自身的解析回退（Codex 审查 t_15e9ed46 驳回项，2026-10-12 修）

加固版用 `_brace_positions` 的 `in_str` 状态机预判字符串边界、跳过「字符串内」的
`{`，实测这层过滤**会误杀**：模型回复是散文 + JSON 的混合体，散文里的 ASCII 双引号
常不成对，一个落单的 `"` 就把状态永久卡在 `True`，后面合法的 `{…}` 整体漏扫：

```
raw  = '说明 "这是广告 如下\n{"is_ad": true, "confidence": 0.99}'
加固前 _brace_positions 过滤后 = None   → fail-open 放行（比修复前的切片法还弱）
修复后 每个 { 都试 raw_decode   = {'is_ad': True, 'confidence': 0.99}
```

修法是**删掉这层预判**——落在字符串内的 `{` 起点本就解码失败并顺移，预判多余且有害。
补 2 条回归（单元 + 端到端真拦），并用独立探针把旧实现塞回去验证同一输入确实失败、
新实现通过，确认这条守卫会红而不是恒绿。全套 `pytest` **546 passed**。
